# Swimly code and UI audit — 6 September 2026

Historical audit of the previous interface. Current visual and interaction
guidance is in [DESIGN.md](../DESIGN.md).

## Outcome and scope

Reviewed the application routes, shared controls, attendance and progression
flows, server actions, authorization, club scoping, capacity guards and project
documentation. Implemented the concrete issues found while retaining the existing
domain model and Astryx architecture.

The visual reference is [Astryx](https://astryx.atmeta.com/), checked against
the installed `@astryxdesign/core` and Neutral theme 0.5.2 documentation through
the Astryx CLI. [DESIGN.md](../DESIGN.md) supplies Swimly's additional requirements:
44px touch targets, one page heading, responsive tables, semantic status metadata
and support for both colour modes.

This is a code review and browser audit, not a formal accessibility certification
or research with staff. No database records were changed, and no migrations,
imports or seeds were run for verification. Application browser requests were restricted to GET
and HEAD. Interactive save tests used synthetic fixtures with action doubles.

## Findings addressed

| Priority | Finding and user impact | Implemented change |
|---|---|---|
| P1 | Several actions trusted records from the wrong club or checked mutable state before obtaining a capacity lock. Concurrent edits could act on stale enrolments or bookings. | Scoped action lookups to the current club; re-read enrolment, course and assessment state under shared locks; lock transfer courses in a stable order and serialize placement decisions for the swimmer. |
| P1 | A mutation could commit before its audit entry, leaving a changed record without its history if auditing failed. | Put related writes and audit entries in the same transaction across enrolment, assessments, curriculum, classes, swimmers, staff, roles, clubs, attendance and progression actions. |
| P1 | Attendance re-submission rewrote unchanged swimmers' recorder information; note-only changes could be missed. | Compute changes from status and note, write only changed swimmers, include note changes in the audit, and commit the register and class note together. |
| P1 | A class note was not included in the attendance browser draft. Storage errors and failed requests could interrupt recovery. | Versioned drafts retain marks and class notes, support older drafts, validate restored data and report unavailable browser storage. Save failures preserve values and offer a retry path. |
| P1 | Two staff editing the same register could overwrite one another, including after a draft reload. | Add a content revision checked under the course lock. Conflicts return saved values for explicit comparison; drafts retain their original revision; cover changes use the same lock. Identical retries remain write-free. |
| P1 | Dirty attendance and deck state could carry across dates when React reused the component. | Key internal form state by record identity. Same-record refreshes preserve edits; changing class/date or deck level remounts the form and restores only the relevant draft. |
| P1 | A password change could overwrite a concurrent staff reset. Bcrypt accepts only the first 72 bytes of a password. | Compare the original hash in the transactional update, audit it atomically, and validate the UTF-8 byte limit for newly set passwords. |
| P2 | Some narrow-screen tables hid useful context, role actions were cramped, and timetable selectors had 20px touch targets. | Re-home secondary information into mobile rows, wrap role actions, stack paired dialog fields on phones, and apply 44px minimums to the actual Astryx input and selector controls. |
| P2 | Status colours appeared directly at call sites, and selected swimmers used an invalid nested interaction. | Centralize status metadata; use Astryx Token's link and remove controls as siblings; constrain and sanitize Together selections. |
| P2 | Shared form adapters dropped native attributes, and controls could retain stale values after reset or URL navigation. | Forward native validation/autofill attributes, exclude disabled fields from form data, reset controlled adapters, and remount search state when its URL query changes. |
| P2 | Rejected or hung saves could leave a dialog pending, allow repeated requests, or lose a clear recovery message. | Catch shared form/action failures, retain input, block duplicate submits and dismissal while pending, and restore the retry path after an unconfirmed save timeout. |
| P2 | Astryx SegmentedControl does not deselect an option on a second tap, so the documented competency undo interaction did not work. | Add an explicitly labelled Astryx clear button to both competency checklists, with pending/read-only guards. |
| P2 | Theme controls and a sticky save label were cramped on phones; some headings and navigation labels were incomplete. | Use compact text theme choices, prevent the save action shrinking, provide the wrong-club page heading and name the navigation landmark. |
| P2 | Impossible dates could normalize into a different day, and displayed timestamps depended on the server's timezone. | Validate date-only input by calendar round-trip and format timestamps in Europe/Dublin. |
| P3 | Repeated keyholder queries and no-op writes did unnecessary work. Project setup docs still identified superseded visual systems. | Read users/roles once for both keyholder checks, expand shared roles once, avoid unchanged mutations, centralize the app name, and update README/DESIGN to Astryx. |

New transfers out of a waitlist close the waiting booking as withdrawn and name
the waitlist in the audit, instead of implying that the swimmer occupied it.
Historical attendance remains conservative: active enrolments covering the date
plus existing saved attendance. Older terminal enrolment statuses do not reliably
distinguish former waitlist entries from occupied places. This audit does not
invent historical attendance eligibility from those ambiguous rows.

## Verification

The following checks were run against the changed application:

- `npm run typecheck` — passed.
- `npm run lint` — passed without application warnings or errors. Generated
  clients, vendored skill sources and temporary browser bundles are excluded.
- `npm test` — 49 regression tests passed, including simultaneous register saves,
  stale class notes, review of legacy drafts, lost-response retries, real Auth.js
  session handling with synthetic tokens and PostgreSQL TLS configuration.
- `npm run build` — passed, including Prisma client generation and all Next.js
  routes. It did not apply database migrations.
- `git diff --check` — passed.

The regression suite executes real action modules with explicit database and
authentication doubles. It covers club boundaries, concurrent state changes,
capacity/placement guards, atomic audit rollback, unchanged submissions,
attendance drafts, calendar input, password races and keyholder access.

The read-only route matrix covers 20 route variants at **375, 768, 1024 and
1280px in light and dark**: overview, Today, swimmers, timetable (today and all
days), Together, assessments, programmes, staff, roles, clubs, activity, account,
and representative swimmer/class/programme/assessment detail and deck routes.
Each check waits for streamed page content before measuring the visible heading,
main landmark, overflow, nested controls and touch target heights. The original
runtime checks recorded uncaught page errors only; the follow-up now also records
browser console errors, including server errors forwarded by Next.js.
The repeated **160 checks passed**: all routes returned 200, with one visible H1 and
main landmark, no page overflow, no nested links/buttons, no undersized controls
at the touch widths, no browser console errors and no uncaught page errors.
Detail samples are representative records, not every possible database state.

### Follow-up: Next.js runtime errors

The user's existing browser repeatedly reported `JWTSessionError: no matching
decryption secret`. Next.js's development MCP diagnostics confirmed these server
console errors while reporting no compilation issues. A fresh browser context
missed the problem because it lacked the stale Auth.js cookie. A synthetic token
encrypted with another secret reproduced the error before the fix.

Development sessions now use a Swimly-specific cookie, preventing collisions with
the generic Auth.js cookie shared by localhost apps across ports. Production keeps
its existing cookie names. Tests verify real Auth.js decoding and renewal, cookie
security flags over HTTP/HTTPS, production compatibility and rejection of invalid
tokens; logging and signature checks remain enabled.

The PostgreSQL driver also warned that its legacy SSL aliases would change
semantics in a future release. Connection setup now makes their current full
certificate and hostname verification explicit with `verify-full`, preserving
an explicitly requested libpq compatibility mode. No credentials or database
records were changed.

After restarting the development server and refreshing the user's browser,
Next.js reported no configuration, compilation or browser runtime errors.
All **20 sampled routes** returned 200 without console errors or uncaught page
errors even with the stale synthetic cookie present. The full 160 viewport/theme
checks also passed with console-error detection enabled. Build, typecheck, lint
and the 49 regression tests passed. The restarted server log contained no server
or browser errors, session decryption errors or SSL warnings.

Separate synthetic browser checks exercise form submission/reset, rejection and
timeout recovery, blocked localStorage, legacy/current attendance drafts,
competency clearing, dirty refreshes, switching dates and returning to each
record's own draft, and read-only controls. Shared form layouts
cover eight viewport/theme combinations; register and deck layouts cover sixteen.
Synthetic phone and desktop screenshots were visually reviewed for light/dark
rendering, field containment, action visibility and truncation.

The continuation added eight viewport/theme checks for the register comparison
screen and exercised its explicit overwrite, saved-version adoption, revision
retention through retry/reload and automatic keyboard focus. Resolved text and
field colours on the synthetic register, competency and comparison screens were
measured across 24 combinations after theme transitions settled: no sampled
contrast failures, with a minimum ratio of **5.06:1**. The measurement composites
DOM background layers and excludes disabled/hidden text; it is not a complete
audit of images, pseudo-elements or every interaction state.

The updated real register route also passed eight read-only integration checks
across the required widths and themes, with no runtime errors or page overflow.
Its anonymous metrics are in `register-integration-results.json` alongside the
other local evidence.

Keyboard checks in both themes confirm that the first Tab reaches "Skip to
content", activation focuses the main landmark, and a focused theme control has
Astryx's visible 2px outline. Reduced-motion styles are retained. Astryx's
pointer-only tab-strip scroll button is intentionally `aria-hidden` and removed
from the tab sequence; the actual tabs provide keyboard navigation.

Local evidence is kept under `.impeccable/review/` (ignored by Git):
`browser-results.json`, `keyboard-results.json`, `shared-controls/results.json`,
`deck-controls/results.json`, and synthetic screenshots in the two control
directories. No real swimmer names, contact details or medical notes are included
in these exported results.

## Limits and follow-up

- Full screen-reader sessions, contrast measurements of every component state,
  physical wet-touch testing and staff usability sessions were not performed.
  Application colours use Astryx's theme and tag tokens; browser chrome metadata
  mirrors Neutral's background-body values because metadata cannot resolve CSS
  custom properties.
- Concurrency regression tests model relevant interleavings with isolated doubles.
  They do not replace a PostgreSQL concurrency/load test on a separate database.
- Save timeouts do not cancel work already running on the server. The UI therefore
  says the result is unconfirmed and preserves values; it does not promise that
  nothing committed. Register saves now guard against conflicting versions;
  competency edits still have no equivalent multi-user comparison workflow.
- No measured speedup or load-test result is claimed. The performance changes
  remove redundant reads/writes and retain the existing bounded search and
  pagination design.
- No dependency upgrade, destructive cleanup, schema migration or deployment was
  part of this refactor. Existing instruction/skill adaptations remain preserved.
